# ui
- Customer-facing QR codes (e.g., QRIS payment images) must be large enough to scan easily on both tablets and mobile devices — use fluid widths (w-full + max-w) so they scale up on bigger screens. Confidence: 0.65
- Customer-facing images like the QRIS code should be clickable/tappable to open a fullscreen overlay showing the full-size image, so customers can zoom in and scan more easily. Confidence: 0.7
- Dialogs must never overlap/overflow the screen on small devices — cap content height (e.g., max-h-[90vh] with overflow-y-auto) and size embedded images conservatively (e.g., max-w-[300px]) so all content fits and remains scrollable when vertical space is limited. Confidence: 0.65
- All action buttons in a dialog must be visible without scrolling — compact the layout (shrink image, tighten padding/spacing, reduce container width) so no action is hidden below the fold; avoid scrolling to reach buttons. Confidence: 0.7
- Button color semantics in dialogs: destructive/cancel actions use red (danger-alert), pending/unpaid status actions use orange (warning-debt) — e.g., "Batalkan Transaksi" red, "Belum Dibayar" orange. Confidence: 0.7
- Status action buttons in a detail view should only be shown when applicable to the current state — e.g., a paid QRIS transaction shows no "Belum Dibayar" (mark-as-unpaid) action, since reverting a completed payment is not offered. Confidence: 0.55
- Avoid cluttered inline action rows in detail/list views; when a row has many actions (edit, delete, etc.), use a mobile-style swipe-to-reveal (slide left) gesture to expose them, mirroring the companion Android app's interaction patterns. Confidence: 0.6
- Prefers a premium modern SaaS visual style (Linear / Stripe / Notion / Shopify POS / Material 3 quality): generous whitespace, 12–16px rounded corners, soft shadows, subtle borders, clear hierarchy, smooth transitions; explicitly avoids outdated admin-dashboard aesthetics (dense tables, heavy borders, cluttered layouts, too many colors, tiny buttons, oversized dialogs, inconsistent spacing). Confidence: 0.85
- Mobile-first: primary target is Android phones (then tablet/desktop) — large touch targets (≥44px), thumb-friendly reachable layouts, sticky action buttons (cart summary, checkout), avoid horizontal scrolling. Confidence: 0.85
- Use a token-based design system (4pt/8pt spacing, border-radius scale, elevation/shadow levels, semantic color tokens, typography scale) and build reusable shared components instead of page-specific designs (design-system-first). Confidence: 0.8
- Prefer extending an existing shared component with a new mode/prop over creating a near-duplicate component for a new feature (e.g., ScannerDialog gained a "receipt" mode for QR scanning instead of a separate scanner). Confidence: 0.55
- Every page needs loading states (skeleton/shimmer), empty states (icon/illustration + helpful explanation + primary CTA), and error states (clear explanation + suggested action + retry button). Confidence: 0.85
- Follow WCAG AA accessibility: high contrast, keyboard navigation, screen-reader support, visible focus indicators, and prefers-reduced-motion support for animations. Confidence: 0.8
- On mobile, prefer bottom sheets for contextual/secondary panels (cart, detail views) and responsive centered dialogs on desktop. Confidence: 0.7
- Prefer responsive card lists over dense tables on mobile; use modern data tables on desktop only. Confidence: 0.75
- Tab layouts should stack vertically — tabs on top, content/sections below — not side-by-side (tabs left, content right). Confidence: 0.7
- Active/selected UI states (e.g., the active tab) must be clearly highlighted and distinguishable so users can tell which item is selected — avoid near-invisible active styling (e.g., a plain white pill on a white card); use the brand color for the active state. Confidence: 0.65
- Support user-selectable color themes (multiple curated palettes) with instant application, smooth animated transition, persistence across sessions, and preview cards showing palette + component mockups before selecting. Confidence: 0.7
- Design for eye comfort in long daily sessions (POS used many hours a day): muted, low-saturation palettes; avoid bright/neon/oversaturated colors; neutral backgrounds, soft shadows, generous whitespace, minimal visual noise. Confidence: 0.75
- Semantic status colors (success/warning/danger/info/error) must stay constant across themes — they carry universal meaning and must not be themed. Confidence: 0.75
- Surfaces must use semantic tokens (bg-card/bg-surface), never literal bg-white/bg-black or hardcoded hex in components, so theming and future dark mode work without per-component changes. Confidence: 0.75
- Theme architecture must be scalable: adding a new theme should only require a new token set, no component code changes — implement theming at the CSS-variable/token layer so the whole app recolors instantly. Confidence: 0.65
- When visual beauty conflicts with usability, usability wins — never add complexity without a measurable usability benefit; keep the product simple and approachable for non-technical users (UMKM owners/cashiers). Confidence: 0.7
- Dashboard and report surfaces must be actionable, not raw stats: every KPI/card should answer "what action should the owner take?", with auto-generated plain-language insights and recommendations (e.g., "sales up this week", "5 products unsold for 30 days") rather than charts alone. Confidence: 0.75
- Cashier/transaction speed is the highest-priority experience — common sales should complete in under ~15 seconds, and every common task should require as few taps/clicks as possible (reduce navigation, add shortcuts). Confidence: 0.65
- Desktop keyboard shortcuts on the cashier screen are wanted for speed: "/" focuses the product search, F2 opens the barcode scanner (on non-kasir pages, "/" opens the global command palette). Confidence: 0.6
 Dashboard = operational overview ("How is my business performing today?"); Reports = analytical view ("Why is my business performing this way?") — keep these responsibilities separate; detailed financials/capital/best-sellers belong on Reports, never mixed back into the Dashboard. Confidence: 0.8
- Primary KPIs must be visible without scrolling on phones — e.g., the four most important KPIs in a 2-column grid above the fold; never place secondary information above primary KPIs. Confidence: 0.75
- Business insights must be compact one-liners (max ~3, each ≤2 lines) with a "View All" link to a full page — never large insight cards or paragraphs that dominate the dashboard. Confidence: 0.7
- Group related financial metrics into one compact card (e.g., income/expense/net profit/margin combined) instead of many separate stat cards. Confidence: 0.65
- Use color sparingly: primary color only for important actions, neutral backgrounds, and semantic colors (green/red/orange/blue) only when they carry meaning — avoid colorful dashboards. Confidence: 0.7
- Design each page to answer a specific question within ~3 seconds of scanning; every section should be recognizable without reading every word. Confidence: 0.7
- Keep the checkout/kasir page focused on the core sale flow — hide product-discovery sections (favorites, best-sellers, recently-sold/new products) from the product area; they clutter the primary task of searching/adding items. Confidence: 0.7
- Avoid duplicate action entry points for the same operation: when both a floating action button (FAB) and an in-page header button add the same thing (customer, capital, expense), remove the FAB and keep the header button; likewise remove floating shortcut buttons on the dashboard that duplicate navigation already available. Confidence: 0.7
- Long-running operations (e.g., Bluetooth printing) must show a visible progress overlay with staged status (connecting → preparing → printing → completed) and, on failure, a meaningful error message plus a retry action — never freeze the UI or rely on toast-only feedback for device operations. Confidence: 0.6
- Receipt printouts should use emphasis sparingly: only the store name gets bold + double-size; Total/Cash/Change (TOTAL/TUNAI/KEMBALI) lines print at normal size and normal weight — oversized/bolded financial lines on a receipt are treated as a bug. Confidence: 0.7
- Receipts must always show the fixed store identity (fall back to the app/store name constant) and must never print the printer's hardware/device name (e.g., a Bluetooth printer label like "RPP02N") or other device identifiers on customer-facing printouts. Confidence: 0.7
- Customer-facing printouts (thermal receipts, WhatsApp receipts, PDF exports) must not include app marketing taglines (e.g., "Catat. Kelola. Tumbuh." / "Record. Manage. Grow."). Confidence: 0.6
- Receipt printouts must look neat: text must not start mid-line or wrap awkwardly — avoid double-centering (formatter space-padding combined with the printer's own ESC/POS centering command pushes text off-center), and wrap long item names to a narrower column with indented continuations instead of running edge-to-edge. Confidence: 0.7
- Store identity on receipts (address/phone) must come from fixed default constants printed automatically on every receipt — users should not have to re-enter address/phone in the settings page; keep settings minimal with a read-only info display, and a blank address/phone on a printed receipt is a bug (e.g., callers passing an empty persisted-store value that overrides the constant). Confidence: 0.8
- Printing must not show a printer-selection popup on every receipt: silently reconnect to the already-granted saved device (e.g., navigator.bluetooth.getDevices()) and keep the connection alive; the chooser should appear only on first-time pairing. Confidence: 0.7
- Receipt printouts must look neat and truly centered: centered header lines must be balanced on both sides and never double-centered (formatter space-padding combined with the printer's own centering command pushes text toward the middle of the line); long item names should wrap to a narrower column with indented continuations rather than running edge-to-edge. Confidence: 0.6
- Printing must not show a printer-selection/chooser popup on every print: keep the GATT connection alive across prints and silently reconnect to the already-granted saved device (e.g., via navigator.bluetooth.getDevices()); the chooser should appear only on first-time pairing. Confidence: 0.7
- Thermal printouts must print dark, crisp, solid-black text: send proper printer init/density commands (ESC/POS reset, charset selection like CP437, darkness/density level), and map non-ASCII glyphs to the printer code page instead of dropping them — faded/light text or mangled characters on a receipt is treated as a quality bug. Confidence: 0.6
- Keep receipts compact and conserve paper: avoid bulky additions that add length (e.g., a QR raster added per feature request was removed because it was "too long and wastes paper") and minimize blank lines and extraneous sections. Confidence: 0.6
